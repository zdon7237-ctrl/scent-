# 气味档案真实线上平台改造计划

更新日期：2026-05-06

## 当前结论

项目当前已经从纯静态展示页发展成一个可本地运行的电商开发版：

```text
静态页面 + 本地 Node API + JSON 数据库 + 会员/订单/积分/积分商城闭环
```

下一阶段目标不是继续堆页面，而是把系统从“本地演示可用”改造成“真实线上可运营”。优先级应当围绕四件事：

1. 数据可靠。
2. 支付可信。
3. 后台安全。
4. 订单履约完整。

推荐路线：

```text
测试兜底 -> 正式数据库 -> 后台登录权限 -> 真实支付 -> 订单履约 -> 部署监控 -> 真实内容运营
```

## 线上 MVP 标准

达到以下标准，才算进入真实线上平台的第一版：

| 模块 | MVP 标准 |
|---|---|
| 数据 | 用户、会员、订单、积分、积分商城、后台日志使用正式数据库，不再依赖 JSON 文件 |
| 账户 | 会员登录、管理员登录都有安全会话、密码哈希、退出和基础防护 |
| 后台 | 不再使用 `dev-admin`；后台 API 需要管理员身份和权限 |
| 支付 | 接入真实支付渠道，支付回调有签名校验、幂等处理和订单金额校验 |
| 订单 | 用户可填写收货地址；后台可发货、填写物流单号；用户可查看订单状态 |
| 积分 | 确认收货后发积分，退款扣回，积分商城 FIFO 消耗和取消返还规则稳定 |
| 部署 | 有生产环境变量、HTTPS、日志、错误监控、数据库备份和恢复方案 |
| 前端 | 使用真实商品/品牌内容；移动端购买链路可用；错误、空状态、加载状态清楚 |
| 合规 | 至少准备服务条款、隐私政策、退换货说明、支付与配送说明 |

### 继续补齐


### 验收

- 不污染真实本地开发数据库。

## 阶段 1：迁移到正式数据库

### 目标

用 PostgreSQL 替换 `server/data/db.json`，保持现有业务行为不变。

### 推荐选择

首选 PostgreSQL。原因：

- 订单、积分、退款、库存都需要事务。
- 未来后台筛选、报表、会员导出会更容易。
- 云平台支持成熟，备份和迁移方便。

### 数据表建议

第一版至少包含：

| 表 | 用途 |
|---|---|
| `users` | 会员账号、邮箱、手机、密码、状态 |
| `sessions` | 会员登录会话 |
| `admin_users` | 后台管理员账号 |
| `admin_sessions` | 后台登录会话 |
| `member_profiles` | 会员等级、累计消费、可用积分、生日、营销偏好 |
| `member_tiers` | 等级规则、折扣、积分倍数、免运门槛 |
| `orders` | 普通订单主表 |
| `order_items` | 普通订单商品快照 |
| `point_transactions` | 积分流水，含来源批次、兑换、退款、过期 |
| `tier_history` | 会员等级变化记录 |
| `points_mall_items` | 积分商城商品 |
| `points_redemption_orders` | 积分兑换订单 |
| `points_redemption_items` | 积分兑换订单明细 |
| `operation_logs` | 后台操作日志 |
| `payment_events` | 支付回调事件和幂等记录 |
| `addresses` | 用户收货地址 |

### 实施顺序

1. 新增数据库连接层，不直接在业务代码里散落 SQL。
2. 建立迁移脚本，生成初始 schema。
3. 把 `defaultDb` 种子数据迁移为 seed 脚本：会员等级、默认积分商城商品。
4. 把 `readDb/writeDb` 访问替换成 repository 方法。
5. 对订单创建、确认收货、退款、积分兑换使用数据库事务。
6. 保留临时 JSON 迁移脚本，只用于把开发数据导入 PostgreSQL。
7. 跑现有 API 测试，确保业务结果不变。

### 关键规则

- 金额继续使用整数分存储。
- 积分继续使用整数。
- 订单商品必须保存快照，不能依赖后续商品数据变化。
- 积分 FIFO 必须通过 `source_transaction_id` 保持可追踪。
- 库存扣减、积分扣减、订单创建必须在一个事务里完成。

### 验收

- 删除或停用 JSON 数据库后，系统仍可完整跑通测试。
- 并发兑换同一积分商品不会扣成负库存。
- 重复支付回调、重复确认收货、重复退款不会重复结算。

## 阶段 2：正式后台登录与权限

### 目标

把当前 `x-admin-key` 开发密钥替换为正式后台账号体系。

### 功能范围

1. 管理员登录页。
2. 管理员账号创建和密码哈希。
3. 后台 session cookie。
4. 角色权限：
   - `owner`：全部权限。
   - `ops`：订单、发货、退款、积分商城处理。
   - `support`：查看会员、查看订单、处理客服信息。
5. 后台操作日志继续保留，并记录管理员 ID。

### API 调整

新增：

```http
POST /api/admin/auth/login
POST /api/admin/auth/logout
GET  /api/admin/auth/me
```

现有 `/api/admin/*` 接口：

- 从校验 `x-admin-key` 改为校验管理员 session。
- 本地开发可以保留一个 seed 管理员账号，但不能继续把 `dev-admin` 当线上权限。

### 安全要求

- 密码继续使用强哈希，后续可升级为 Argon2 或 bcrypt。
- Cookie 使用 `HttpOnly`、`SameSite=Lax`，生产环境开启 `Secure`。
- 登录失败需要基础限流。
- 后台 API 不返回密码哈希。

### 验收

- 未登录后台不能访问管理接口。
- 不同角色访问权限符合预期。
- 所有后台改动都写入 `operation_logs`。

## 阶段 3：真实支付

### 目标

把“后台确认支付”替换为真实支付渠道，同时保留开发模拟支付能力。

### 推荐路线

国内用户优先考虑：

1. 微信支付。
2. 支付宝。

如果先做跨境或开发验证，也可以先接 Stripe，但国内小众香水买手店更应该优先考虑微信支付/支付宝。

### 支付流程

```text
用户提交订单 -> 后端生成订单 -> 创建支付单 -> 前端跳转/拉起支付 -> 支付平台回调 -> 校验签名 -> 标记 paid -> 用户确认收货后发积分
```

### 必须实现

1. 支付单表或支付事件表。
2. 支付平台回调签名校验。
3. 回调幂等：同一支付事件不能重复处理。
4. 金额校验：回调金额必须等于订单应付金额。
5. 订单状态校验：只有 `pending_payment` 可以变 `paid`。
6. 支付超时关闭订单。
7. 开发环境保留手动支付接口，但只允许本地或管理员使用。

### 验收

- 正常支付后订单变为 `paid`。
- 重复回调只处理一次。
- 金额不一致的回调被拒绝。
- 签名错误的回调被拒绝。
- 支付成功不发积分，确认收货才发积分。

## 阶段 4：订单履约与售后

### 目标

把订单从“支付/确认收货”扩展成真实电商履约流程。

### 普通订单状态

建议统一为：

```text
pending_payment -> paid -> processing -> shipped -> completed
                 -> cancelled
                 -> refunded
```

### 需要补齐

1. 收货地址：
   - 下单时保存收货人、手机号、省市区、详细地址。
   - 订单保存地址快照。
2. 发货：
   - 后台填写物流公司、物流单号、发货时间。
   - 用户订单页显示物流信息。
3. 确认收货：
   - 用户手动确认。
   - 后续可加自动确认收货。
4. 退款：
   - 区分未发货退款、已发货退款、已完成退款。
   - 已完成订单退款继续扣回积分和累计消费。
5. 库存：
   - 普通商品也需要库存字段。
   - 下单扣库存或支付扣库存需要明确，建议支付成功扣库存，超卖风险通过事务控制。

### 验收

- 用户可以提交包含地址的订单。
- 后台可以发货并填写物流信息。
- 用户可以在订单页看到发货状态。
- 退款不会造成积分、累计消费、库存重复变更。

## 阶段 5：商品、库存和运营内容真实化

### 目标

让网站从“演示商品目录”变成可运营商品系统。

### 商品数据

当前商品主要来自 `src/assets/data.js`。线上建议逐步迁移为后台可管理数据：

| 内容 | 建议 |
|---|---|
| 商品 | 存数据库，后台维护 |
| 品牌 | 存数据库，后台维护 |
| 文章 | 初期可继续静态，后续做 CMS |
| 图片 | 使用对象存储或 CDN |
| 库存 | 存数据库并参与订单事务 |
| 价格 | 存数据库，订单保存快照 |

### 后台运营能力

1. 商品上下架。
2. 商品价格、库存、图片、香调、品牌、适合场景编辑。
3. 积分商城商品维护。
4. 订单筛选和导出。
5. 会员筛选和导出。
6. 文章和买手笔记管理可以后置。

### 验收

- 下架商品不能购买。
- 价格变更不影响历史订单。
- 商品图片来自稳定地址，不依赖 Unsplash 占位图。

让系统可以稳定运行在真实服务器或云平台。

第一版可以采用：

```text
Node 服务 + PostgreSQL + 对象存储/CDN + HTTPS 反向代理
```

部署前必须有：

1. 生产环境构建命令。
2. 生产启动命令。
3. 数据库迁移命令。
4. 日志输出。
5. 错误监控。
6. 数据库自动备份。
7. 回滚方案。

### 验收

- 新环境从空数据库迁移后可启动。
- 健康检查接口可用。
- 服务重启后用户和订单数据不丢。
- 错误日志可追踪到请求和用户/订单上下文。

4. 购物车。
5. 登录/注册。

### 必须补齐的状态

- 表单校验失败。
- 未登录跳转。
- 支付处理中。

## 阶段 8：安全、合规和运营准备

### 安全清单

1. 密码哈希和登录限流。
2. 管理员权限校验。
3. CSRF 风险评估。
4. Cookie `HttpOnly`、`SameSite`、生产 `Secure`。
5. 输入校验和输出转义。
6. 支付回调签名校验。
7. 管理接口限流。
8. 错误信息不泄露内部路径、密钥和 SQL。

### 合规与内容

上线前至少准备：

- 隐私政策。
- 用户服务协议。
- 配送说明。
- 退换货说明。
- 支付说明。
- 联系方式。
- 商品正品来源说明。

具体法律文本需要按实际经营主体、地区和支付渠道要求确认。
